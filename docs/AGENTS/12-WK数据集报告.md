# 12 · WK 数据集报告（v2）

## 1. 目的与范围

本数据包为律师求生者 VLA 的 WK（World Knowledge）阶段准备短问答，服务于
“看见了什么状态，接下来允许做什么”的文本知识后训练。它只面向官方自定义剧本、
训练营和沙盒环境；不包含真人排位数据、内存读取、DLL 注入或截帧 hook。

WK 是文本知识后训练，不是逐帧控制标签；它不能替代 VG 的画面证据，也不能替代
ACT 的 3 帧观测到未来 4 步动作块监督。当前硬件为 RTX 2080 Ti（无 BF16），
后续建议以 FP16 + GradScaler 的小规模 LoRA/QLoRA 做 WK 训练。

## 2. 数据来源

数据文件位于 `idv_agent/data/wk/`：

- `wk_train.jsonl`：70 条 WK v2 短问答（每行一条 JSON）。
- `knowledge_gaps.json`：7 条知识缺口，不进入训练集。

来源以 BWIKI 第五人格 wiki 为主站（页面明确声明“本WIKI是玩家自建的WIKI，与官方
有合作但不要将本WIKI视作官方站点”），另有项目记录锚点文档
`docs/13-WK数据来源与锚点.md`：

- 匹配模式：人数、密码机目标、QTE、板窗、箱子、治疗、恐惧值、地窖、大门、乌鸦。
- 联合狩猎模式：人数、密码机目标、胜负、电话亭、双持、地窖/撬棍、禁锢阶段。
- 黑杰克模式：5 人、21 点、双身份、回合制、牌库、筹码商城、伤害。
- 律师/进阶：律师手绘地图、要点记录、郎心似铁。
- 道具：手绘地图耐久、工具箱拆除时间、联合/黑杰克道具。
- 治疗：治疗相关术语定义。

读取时间为 2026-09-01；页面状态、更新时间和版本适用范围仍需人工复核。

## 3. 数据格式

每行一个 JSON 对象，字段结构（v2 严格按此）：

```json
{
  "id": "wk_000001",
  "question": "匹配模式下每局双方各有多少名玩家？",
  "answer": "匹配模式为 1 名监管者对抗 4 名求生者的非对称竞技模式，双方共 5 名玩家。",
  "mode": "standard",
  "topic": "rule",
  "episode_id": "wk_rules_v2",
  "split": "train",
  "source": {
    "title": "第五人格 BWIKI：匹配模式",
    "url_or_path": "https://wiki.biligame.com/dwrg/...",
    "source_type": "verified_community",
    "quote_or_excerpt": "支撑该答案的原文摘录"
  },
  "verification": {
    "status": "reviewed",
    "review_note": "人工审核确认锚点，直接采信。"
  }
}
```

`mode` 仅允许 `standard`、`joint_hunt`、`blackjack`，与 `<mode:...>` 条件 token
一致。`topic` 仅允许 `rule`、`object`、`state`、`interaction`、`mode`。
`split` 固定为 `train`（v2 单文件输出）。

## 4. 类别和状态定义

五类主题：

- `rule`：规则（人数、密码机目标、胜负判定、淘汰流程、QTE、开箱/换道具、地窖）。
- `object`：对象语义（密码机、狂欢之椅、板/窗、箱子、电话亭、地窖、大门、道具）。
- `state`：状态转移（受伤/倒地/上椅/淘汰、自愈、治疗、眩晕、擦刀、心跳/红光、乌鸦）。
- `interaction`：交互前置（破译、救援、翻越、治疗、道具、开门各自的触发条件与键位）。
- `mode`：模式差异（standard / joint_hunt / blackjack 的独立采证差异）。

审核状态：

- `reviewed`：人工审核确认锚点（匹配 1v4/7 机 5 台、联合狩猎 2v8/11 机 7 台/
  胜负/电话亭/双持、求生者键位 WASD/Q/Space/E/F/Shift/Ctrl/T/X）直接采信；
  或同一 WIKI 多页面交叉支撑并已复核的条目。
- `needs_review`：单一社区来源或仅项目记录支撑，尚未经官方说明/游戏内复核，
  进入训练前必须完成复核并更新状态。

`answer` 只写直接知识陈述；审核状态只出现在 `verification.status`，不进入
`answer`。

## 5. 清洗规则

校验脚本为 `idv_agent/scripts/validate_wk_v2.py`，执行：

```powershell
python -m idv_agent.scripts.validate_wk_v2
```

检查项：

- JSONL 解析与必填字段（id/question/answer/mode/topic/episode_id/split/source/verification）。
- 条目总数 50-100，五类 topic 每类 ≥ 8。
- id 与 question 唯一，归一化相似度 ≥ 0.94 的近重复问题检测。
- `answer` 不含「候选 / 待核验 / 不得进入训练 / 仅作为清单」等元描述。
- `mode` / `topic` / `source_type` / `verification.status` 枚举合法。
- source 的 title / url_or_path / quote_or_excerpt 非空；`project_record` 路径存在。
- `knowledge_gaps.json` 结构合法、gap id 唯一。

本项目没有 `keymap.json`，只有 `idv_agent/configs/keymap.py`；键位条目以人工审核
锚点为来源（`docs/13-WK数据来源与锚点.md`），未伪称与 keymap.py 一致，
Shift/Ctrl/T/X 的登记差异已记入知识缺口。

## 7. 仍需人工审核的样本

52 条 `needs_review` 均为单一社区来源（BWIKI）支撑，主要涉及：

- 匹配模式数值细节：QTE 回退、合作破译惩罚、治疗时长、倒地淘汰 240 秒、
  受击加速、心跳半径、三鸦聚顶、开箱/搜寻时长。
- 联合狩猎数值细节：破译 95 秒、开门 32 秒、禁锢 40 秒、地窖/撬棍规则。
- 黑杰克全部机制条目：回合制、牌库、筹码商城、伤害、21 点与决胜规则。
- 律师手绘地图功能与耐久数值。

这些条目只有在取得当前版本官方说明（`official`）或受控沙盒录制加双人审核后，
才能改为 `reviewed`。不得用模型生成答案或未核验社区帖替换来源。

## 8. 可能的数据偏差

- 规则数值主要来自单一社区 wiki，缺少版本化官方来源；数值条目占比高，
  版本更新后容易过时。
- 律师相关的对象/交互条目偏少，`object` 以通用对象为主，不代表律师整局分布。
- 黑杰克、联合狩猎条目依赖页面描述，未经本地游戏画面验证。
- 文本问答是短格式，可能让模型学到规则表述而非可泛化的因果判断；
  必须用独立 VG/ACT 评估验证，而不是只报告 WK 准确率。
- 键位锚点与项目 keymap.py 未完全同步（Shift/Ctrl/T/X），存在配置漂移风险。

## 9. 对 WK / VG / ACT 的后续建议

1. 为 52 条 `needs_review` 补充版本日期、官方链接/存档摘录和审核人，复核后
   更新状态并按 episode 重新切分 train/val/test。
2. 在官方自定义剧本或训练营录制独立 session，采集可见密码机、墙后高亮、
   交互提示、破译状态、误检、卡墙与目标丢失样本；每个 VG 图像记录
   `image_source`、真实 `session_id`、地图/分辨率、标注者和审核状态；按 session
   切分，绝不随机拆相邻帧，也不做水平翻转。
3. 同步 `keymap.py`（或建立 keymap.json）到人工锚点键位，消除配置漂移。
4. ACT 只接收已通过 `validate_vla_raw` 的 `vla_raw` session，保留 3 帧观测、
   `<mode:...>`、历史动作到未来 4 步动作块。WK 的 Q/状态知识只帮助理解提示，
   不能替代动作块标签或真机成功验证。
5. 先用 18 条 reviewed 数据做极小 LoRA 连通性实验和留出集检查；2080 Ti 使用
   FP16 + GradScaler。真发送仍只限自定义剧本/训练模式并先 dry-run。

## 10. 候选内容边界

以下内容只是候选，不能直接进入训练：

- 全部 `needs_review` 条目（52 条）在复核完成前不得作为已核验知识训练。
- `knowledge_gaps.json` 中 7 条缺口（keymap 不同步、狂欢之椅独立机制页缺失、
  黑杰克版本一致性、角色道具完整列表、扳手图标/黄色高亮视觉证据、
  官方版本化规则、联合狩猎限时混沌效应）均未进入训练集。
- 狂欢之椅独立页面实际是归宿家具页，不是对局机制页，不能作为机制来源。
